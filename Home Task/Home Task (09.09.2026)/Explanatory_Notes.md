Это веб‑приложение со списком задач. Страница со списком рендерится на сервере (Razor), а сами задачи подгружаются на клиенте через fetch‑запросы к JSON API. Данные лежат в двух JSON‑файлах на диске и читаются при каждом запросе.

---

## Шаг 1. Запуск и регистрация зависимостей

При старте подключается MVC и регистрируются два репозитория как **singleton**:

- репозиторий задач — читает `Data/tasks.json`;
    
- репозиторий версий — читает `Data/versions.json`.
    

Репозитории ничего не кешируют: каждый вызов заново открывает файл, десериализует его целиком в список и фильтрует в памяти. Singleton здесь означает лишь, что экземпляр класса один на всё приложение; состояние между вызовами не сохраняется.

Дальше настраивается стандартный конвейер: HTTPS‑редирект, статические файлы, маршрутизация, маршрут по умолчанию (главная → домашний контроллер).

---

## Шаг 2. Открытие главной страницы (GET `/`)

Домашний контроллер получает все задачи из репозитория, вытаскивает из них **уникальные категории**, сортирует их по алфавиту и кладёт в модель представления вместе с заголовком и адресом API (`/api/tasks`).

Важно: сами задачи в HTML **не встраиваются**. В модель попадают только заголовок, адрес API и список категорий. Список задач строится на клиенте.

Представление `Index.cshtml` рендерит:

- заголовок;
    
- четыре кнопки‑фильтра: «Все», «Новые», «В работе», «Выполненные» — у каждой в `data-status` лежит соответствующее значение статуса (или пустая строка для «Все»);
    
- контейнер `#tasks`, в `data-endpoint` которого лежит адрес API, а в `data-loading-text` — текст «Загрузка задач…»;
    
- шаблон карточки задачи `<template id="task-card-template">` с пустыми местами под поля (заголовок, категория, статус, приоритет, срок, кнопка «Версии»);
    
- скрытый блок ошибок `#tasks-error`.
    

В конце страницы подключается `tasks.js`.

---

## Шаг 3. Загрузка списка задач на клиенте

Скрипт `tasks.js` обёрнут в IIFE со строгим режимом. Сначала он находит контейнер `#tasks`; если его нет — сразу выходит (то есть скрипт безопасно подключать на любой странице).

Далее:

1. Читает из `data-*` адрес API и текст загрузки, находит шаблон и блок ошибок.
    
2. Определяет вспомогательные функции: показать/скрыть ошибку, отформатировать дату в русский формат (или «—», если дата невалидна).
    
3. Определяет функцию рендера: если массив задач пуст — пишет «Задач не найдено»; иначе клонирует шаблон для каждой задачи, заполняет поля по `data-field`, кладёт в кнопку «Версии» идентификатор задачи, собирает всё в `DocumentFragment` и одной операцией заменяет содержимое контейнера.
    
4. Определяет функцию загрузки: очищает ошибку, ставит текст «Загрузка задач…», формирует URL (с параметром `status`, если фильтр задан), делает `fetch` с заголовком `Accept: application/json`, проверяет `res.ok`, парсит JSON и рендерит. При любой проблеме (сеть, HTTP‑ошибка) показывает сообщение в блоке ошибок.
    
5. Навешивает обработчики на кнопки‑фильтры: клик → загрузка с соответствующим статусом (или без него для «Все»).
    
6. Навешивает **делегированный** обработчик клика на контейнер задач — так он работает и для карточек, которые появятся позже.
    
7. Сразу вызывает загрузку без фильтра — список отображается при открытии страницы.

## Шаг 4. Запрос списка к API

Клиент обращается к `/api/tasks` (или `/api/tasks?status=New` и т. п.). Контроллер API:

- если параметр `status` пустой или состоит из пробелов — берёт **все** задачи;
    
- иначе — только с указанным статусом.
    

Сравнение статуса **регистронезависимое** (OrdinalIgnoreCase), поэтому `new`, `New`, `NEW` сработают одинаково.

Контроллер возвращает `200 OK` с массивом задач в виде JSON. Клиент рендерит карточки.

Отдельно есть метод получения одной задачи по числовому id: если задачи нет — `404`, иначе `200` с объектом.

## Шаг 5. Клик по кнопке «Версии»

Обработчик на контейнере ловит клик, проверяет, что цель — кнопка с классом `versions-btn` (через `closest`, чтобы работало и при клике по вложенным элементам). Берёт id задачи из `data-id`.

Затем делает запрос к `/api/tasks/{id}/versions`. Контроллер версий:

- возвращает все версии указанной задачи, **отсортированные по номеру версии**;
    
- либо одну конкретную версию по её номеру (если её нет — `404`).
    

Клиент:

- если версий нет — показывает `alert` «У задачи пока нет версий»;
    
- иначе собирает строки вида `v{номер} ({дата создания}): {заголовок}` и, если есть плановые даты, добавляет строку «План: начало → конец» (невалидные/пустые даты превращаются в «—»);
    
- показывает всё через `alert`;
    
- при ошибке пишет сообщение в блок ошибок.

## Шаг 6. Обработка ошибок и краевые случаи

- **На клиенте**: любая сетевая или HTTP‑ошибка ловится в `try/catch`, логируется в консоль и показывается пользователю в `#tasks-error` (блок становится видимым). Перед каждой загрузкой ошибка скрывается.
    
- **На сервере**: если задача/версия не найдена — возвращается `404`, и клиент превращает это в сообщение «Не удалось загрузить… HTTP 404».
    
- **Отсутствие файла данных**: репозиторий не падает — возвращает пустой список. Тогда на странице будет «Задач не найдено», а категорий — пусто.
    
- **Невалидные даты в JSON**: при рендере карточки дата показывается как «—», при показе версий плановые даты тоже становятся «—».
    
- **Приложение вне режима разработки**: при необработанном исключении срабатывает обработчик `/Home/Error` и показывается страница ошибки с идентификатором запроса; в режиме разработки вместо неё — подробности исключения.

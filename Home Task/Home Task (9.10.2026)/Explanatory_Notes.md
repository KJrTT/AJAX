В данном проекте реализованы несколько подходов к аутентификации и авторизации в [ASP.NET](https://asp.net/) Core: cookie‑аутентификация, Bearer‑токены (JWT), паттерн BFF, гибридная схема «cookie + Bearer» с автоматическим выбором. Ниже — теория и логика каждого подхода, а также общие заготовки, которые используются во всех вариантах.

---

## Общие заготовки

Во всех подходах используется одно и то же хранилище пользователей и сервис выпуска токенов.

**Хранилище пользователей** — словарь «имя → пользователь». Пароль хранится не в открытом виде, а как SHA‑256 хеш в Base64. Проверка пароля сравнивает хеши **за постоянное время** (FixedTimeEquals): это защита от атак по времени, когда злоумышленник по задержке ответа пытается подбирать пароль посимвольно. В реальном приложении SHA‑256 для паролей недостаточен — нужен медленный алгоритм (PBKDF2, bcrypt, Argon2), но в учебном примере так.

**Сервис токенов** собирает JWT с полями:

- `sub` — имя пользователя;
    
- `jti` — уникальный идентификатор токена (нужен для отзыва);
    
- `iat` — время выпуска;
    
- роли — отдельными claim‑ами.
    

Токен подписывается HMAC‑SHA256 симметричным ключом. Отдельно сервис умеет генерировать случайный refresh‑токен из 64 байт криптостойкого генератора.

**Хранилища в памяти** (синхронизированные словари):

- отозванные сессии — по `sid`;
    
- отозванные JWT — по `jti`;
    
- refresh‑токены — с именем пользователя и сроком действия.
    

Всё in‑memory: при перезапуске всё забывается, между экземплярами приложения не разделяется.

## Cookie‑аутентификация

Регистрируется схема на основе cookie. Настройки:

- имя cookie, HttpOnly (JavaScript не видит), Secure (только по HTTPS), SameSite=Lax (базовая защита от CSRF);
    
- срок жизни 8 часов со скользящим продлением (активность пользователя продлевает сессию);
    
- пути логина, логаута и отказа в доступе.
    

Ключевой момент — **событие проверки принципала при каждом запросе**. Берётся `sid` из cookie, и если сессия отозвана — принципал отклоняется, пользователь разлогинивается. Это даёт «мгновенный» отзыв сессии, не дожидаясь истечения cookie.

Дополнительно включается antiforgery (защита от CSRF) и Data Protection с сохранением ключей на диск — иначе после перезапуска все cookie станут невалидными, а в нескольких экземплярах приложения ключи должны совпадать.

Маршруты:

- `GET /csrf` и `GET /login` — выдают CSRF‑токен;
    
- `POST /login` — проверяет CSRF, затем логин/пароль. При успехе создаёт `sid`, собирает claims (имя, идентификатор, `sid`, роли) и выпускает auth‑cookie. Возвращает имя и `sid`;
    
- `POST /logout` — проверяет CSRF, отзывает `sid`, удаляет cookie. Требует авторизации;
    
- `GET /me` — возвращает имя и роли или 401. Требует авторизации;
    
- `GET /admin` — только для роли `admin`, иначе 403.
    

Логика: браузер получает cookie, дальше все запросы автоматически аутентифицируются по ней. Отзыв — через чёрный список `sid`, который проверяется при каждом запросе.

## Bearer (JWT) без cookie

Регистрируется только JWT‑схема:

- ключ, издатель, получатель берутся из конфигурации или дефолтов;
    
- проверяются издатель, получатель, подпись, срок жизни (с допуском 30 секунд на рассинхрон часов);
    
- разрешён только алгоритм HMAC‑SHA256 — это защита от подмены алгоритма на «none» или асимметричный;
    
- имя пользователя — из claim `sub`, роль — из claim `role`.
    

Событие после валидации токена проверяет `jti` в чёрном списке: если токен отозван — валидация проваливается.

Маршруты:

- `POST /token` — логин/пароль → access‑токен на 15 минут + refresh‑токен на 7 дней (сохраняется в хранилище). Возвращает токены, тип `Bearer` и `expires_in`;
    
- `POST /token/refresh` — по refresh‑токену: проверяет существование и срок, **отзывает старый refresh** (ротация — одноразовое использование), выпускает новую пару;
    
- `POST /token/revoke` — заносит `jti` текущего access‑токена в чёрный список и отзывает переданный refresh. Требует авторизации;
    
- `GET /me` — `sub` и роли из токена. Требует авторизации;
    
- `GET /admin` — требует claim `role=admin`.
    

Логика: клиент (SPA, мобильное приложение) сам хранит токены и шлёт `Authorization: Bearer …`. Сервер проверяет подпись и срок, плюс чёрный список `jti` для мгновенного отзыва access‑токена. Ротация refresh‑токенов снижает риск: украденный refresh можно использовать только один раз.

## BFF (Backend for Frontend)

Самый сложный подход. Идея: браузер общается с сервером **только по cookie**, а сервер за кулисами ходит в отдельный API по Bearer‑токенам. Токены никогда не попадают в браузер.

Регистрируются **две схемы**: cookie (для сессии браузера) и JWT Bearer (для проверки токенов от API). Плюс две политики авторизации: «Bff» (только cookie) и «Api» (только Bearer). Также antiforgery и HTTP‑клиент с базовым адресом API.

Маршруты на этом сервере:

- `POST /token`, `POST /token/refresh` — те же, что в Bearer‑варианте (для обратной совместимости или тестов);
    
- `GET /api/me`, `GET /api/admin` — требуют именно Bearer‑схему;
    
- `GET /bff/csrf` — выдаёт CSRF‑токен;
    
- `POST /bff/login` — проверяет CSRF, затем шлёт логин/пароль во внешний API по `/token`. Если API ответил успешно — получает пару токенов, генерирует `sid` и **сохраняет токены на сервере** под этим `sid`. Браузеру выдаётся только cookie с `sid` и именем;
    
- `POST /bff/logout` — проверяет CSRF, удаляет серверную запись по `sid`, гасит cookie. Требует Bff‑авторизации;
    
- `GET /bff/me` — берёт `sid` из cookie, достаёт валидный access‑токен из серверного хранилища (при необходимости **обновляет его через refresh**), затем от имени пользователя ходит в API по `/api/me` с Bearer‑заголовком и возвращает ответ как есть. Требует Bff‑авторизации.
    

Ключевой компонент — серверное хранилище сессий: `sid` → (пользователь, access, refresh, срок access). Метод получения валидного access‑токена:

- если токен живёт ещё дольше 30 секунд — отдаёт его;
    
- иначе шлёт refresh‑токен в API, получает новую пару, обновляет запись и отдаёт новый access;
    
- если refresh не сработал — удаляет запись и сигнализирует «не авторизован».
    

Логика: классический BFF. Браузер защищён от кражи токенов (они только на сервере), CSRF закрыт токенами, отзыв — удалением записи по `sid`. Минус — состояние сессий в памяти, не масштабируется без внешнего хранилища.

## Cookies + Bearer одновременно («Smart»)

Гибрид: одна и та же конечная точка может принимать и браузер с cookie, и клиент с Bearer‑токеном.

Регистрируется **политическая схема** «Smart», которая по умолчанию выбирает, какой схемой аутентифицировать запрос:

- если заголовок `Authorization` начинается с `Bearer` — используется JWT‑схема;
    
- иначе — cookie‑схема.
    

Плюс две конкретные схемы (cookie и JWT) с обычными настройками. Плюс две политики: «Html» (только cookie) и «Api» (только Bearer).

Маршруты:

- `GET /csrf` — CSRF‑токен;
    
- `POST /login` — проверяет CSRF, логин/пароль, выпускает cookie с claims (имя, `sid`, роли);
    
- `POST /logout` — проверяет CSRF, гасит cookie;
    
- `POST /token` — логин/пароль → JWT на 15 минут (без refresh);
    
- `GET /dashboard` — только по cookie. Возвращает режим «html» и имя;
    
- `GET /api/data` — только по Bearer. Возвращает режим «api», `sub` и роли (объединяет роли из claim `role` и из стандартного claim роли);
    
- `GET /any` — пускает по **любой** из двух схем (работает «Smart»). Возвращает, какая схема сработала, и имя;
    
- `GET /admin` — требует роль `admin` (подойдёт любая схема).
    

Логика: один сервер обслуживает и классические HTML‑страницы (cookie + CSRF), и API (Bearer). Выбор схемы — по наличию заголовка `Authorization`. Явные политики позволяют точечно требовать нужный способ аутентификации для конкретной конечной точки.

## Что общего и в чём отличия

**Общее**:

- пользователи и токены — в памяти, пароли — SHA‑256 с сравнением за постоянное время;
    
- JWT везде подписывается HMAC‑SHA256, проверяются издатель/получатель/срок/алгоритм;
    
- везде есть механизм отзыва (чёрный список `sid` или `jti`);
    
- везде включён antiforgery там, где есть cookie и POST‑формы;
    
- везде HTTPS‑редирект и порядок middleware: Authentication → Authorization → Antiforgery.
    

**Различия**:

|Подход|Что в браузере|Где токены|Отзыв|Кому подходит|
|---|---|---|---|---|
|Cookie|cookie|на сервере (в claims)|чёрный список `sid`|классический сайт|
|Bearer|ничего (клиент хранит токены)|у клиента|чёрный список `jti` + ротация refresh|SPA, мобильные|
|BFF|только cookie с `sid`|на сервере, отдельно от браузера|удаление записи по `sid`|SPA без хранения токенов в браузере|
|Cookies + Bearer|cookie или токен|и там, и там|по ситуации|один сервер на HTML и API|

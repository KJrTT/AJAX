В данном проекте реализовано защищённое файловое хранилище: загрузка и скачивание файлов через API с аутентификацией по API‑ключу, многоуровневой валидацией содержимого, защитными HTTP‑заголовками и сквозной трассировкой запросов. Отдельно есть страница с «живой» моделью угроз по STRIDE и security backlog — это часть учебного задания по безопасной разработке.

---

## Шаг 1. Запуск и регистрация сервисов

При старте:

- подключается MVC;
    
- настраивается **аутентификация по API‑ключу** — собственная схема `ApiKey`, которая читает заголовок `X-Api-Key`;
    
- добавляются две политики авторизации: `ReadFiles` (роль `Files.Read`) и `WriteFiles` (роль `Files.Write`) — принцип минимальных привилегий: чтение и запись разделены;
    
- регистрируются сервисы: каталог угроз и валидатор файлов — singleton, файловое хранилище — scoped;
    
- настраивается **глобальный лимит Kestrel** на размер тела запроса — 10 МБ. Это защита от DoS ещё на уровне веб‑сервера, до того как запрос дойдёт до приложения.
    

Дальше конвейер middleware в строгом порядке:

1. Обработчик исключений и HSTS — вне Development.
    
2. HTTPS‑редирект.
    
3. Статические файлы из `wwwroot` — публичные JS/CSS, но **не** загруженные пользователями файлы (они лежат вне webroot).
    
4. `RequestIdMiddleware` — проставляет `X-Request-Id` в запрос и ответ.
    
5. `SecurityHeadersMiddleware` — добавляет CSP, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.
    
6. Маршрутизация.
    
7. Аутентификация.
    
8. Авторизация.
    
9. Маршрут по умолчанию.
    

Порядок критичен: middleware безопасности стоят **до** роутинга, чтобы заголовки попадали на все ответы, включая ошибки маршрутизации.

---

## Шаг 2. Аутентификация по API‑ключу

Обработчик читает заголовок `X-Api-Key`:

- если заголовка нет — «результат не определён» (запрос может пойти дальше, но `[Authorize]` его отклонит);
    
- если ключ пустой — отказ;
    
- если ключ совпадает с `ApiKeys:Read` — выдаётся роль `Files.Read`;
    
- если совпадает с `ApiKeys:Write` — выдаются обе роли (`Files.Read` и `Files.Write`);
    
- если не совпал ни с одним — отказ.
    

Ключи берутся из конфигурации, а не из кода. В реальном проекте их хранят в секретах, ротируют и не возвращают клиенту. Сравнение ключей здесь простое (`==`), что теоретически уязвимо к атакам по времени — в продакшене нужно сравнение за постоянное время, как в примерах с паролями.

---

## Шаг 3. Защитные заголовки

`SecurityHeadersMiddleware` ставит разные политики CSP для разработки и продакшена:

- в Development разрешены inline‑скрипты и стили, WebSocket — чтобы работали hot reload и отладка;
    
- в Production — строгая политика: только `'self'`, без inline, `object-src 'none'`, `base-uri 'self'`.
    

Дополнительно:

- `X-Content-Type-Options: nosniff` — браузер не будет «угадывать» MIME‑тип и исполнять файл как HTML/JS, если сервер сказал иное;
    
- `X-Frame-Options: DENY` — страницу нельзя встроить в iframe (защита от clickjacking);
    
- `Referrer-Policy: no-referrer` — URL не утекает на сторонние сайты.
    

---

## Шаг 4. Трассировка запросов

`RequestIdMiddleware`:

- берёт `X-Request-Id` из запроса, если он есть и не длиннее 64 символов;
    
- иначе генерирует новый GUID;
    
- кладёт id в `HttpContext.Items` (доступно внутри приложения) и в заголовок ответа (доступно клиенту);
    
- оборачивает всю дальнейшую обработку в **лог‑scope** с `RequestId`, так что все сообщения логов этого запроса будут помечены одним идентификатором.
    

Клиент (`files-client.js`) тоже генерирует `X-Request-Id` и присылает его. Если что‑то пошло не так, пользователь видит correlation id в сообщении об ошибке и может передать его в поддержку — по нему в логах находится вся цепочка событий.

## Шаг 5. Страница загрузки (MVC)

`FilesController.Index` — тонкий UI: просто возвращает представление. Сама страница содержит:

- поле для API‑ключа (по умолчанию подставлен демо‑ключ);
    
- выбор файла с ограничением по расширениям на клиенте (`accept`);
    
- кнопку «Загрузить»;
    
- прогресс‑бар;
    
- блок результата;
    
- таблицу загруженных файлов (заполняется из localStorage).
    

Страница подключает два скрипта: `files-client.js` (транспорт) и `files-page.js` (логика UI).

## Шаг 6. Клиент API (`files-client.js`)

Это «тонкий» клиент: никакой бизнес‑логики, только транспорт и аккуратная работа с HTTP‑границами.

**Класс ошибки** хранит код, HTTP‑статус и correlation id — это позволяет вызывающему коду различать сценарии (`unauthorized`, `validation_failed`, `network_error` и т. п.).

**Парсер тела ответа** никогда не вызывает `response.json()` вслепую: сначала проверяет `Content-Type`. Если это JSON — парсит; иначе читает как текст (обрезая до 500 символов). Причина: на пути может стоять прокси, антивирус или nginx, которые вернут HTML вместо JSON — клиент не должен на этом падать.

**Общая обёртка `request`**:

- генерирует `X-Request-Id`;
    
- добавляет `credentials: 'same-origin'` — cookie не уйдут на сторонние домены;
    
- поддерживает `AbortSignal` для отмены;
    
- различает сетевые ошибки, abort и HTTP‑ошибки;
    
- маршрутизирует по статусу: 2xx — успех; 401/403 — специальные коды для ре‑аутентификации; 400–499 — ошибки клиента (повторять бессмысленно); 5xx — ошибки сервера.
    

**Загрузка** сделана через `XMLHttpRequest`, а не `fetch`, — только из‑за события `upload.onprogress`, которого у `fetch` в большинстве браузеров нет. Клиентская валидация минимальная: «выбран ли файл» — чтобы не гонять мегабайты зря. Авторитетная проверка всё равно на сервере.

**Скачивание** сначала проверяет формат id регуляркой (`32 hex‑символа`), затем делает запрос и возвращает Blob + имя файла, извлечённое из `Content-Disposition`.

## Шаг 7. Страница загрузки (`files-page.js`)

Логика страницы:

- хранит историю загрузок в `localStorage` под ключом `securefiles.uploads`;
    
- рендерит таблицу с именем, размером (в удобных единицах), типом, id и кнопками «Скачать»/«Удалить из истории»;
    
- при загрузке: блокирует кнопку, показывает прогресс, при успехе добавляет запись в историю и очищает поле выбора файла;
    
- при ошибке различает `unauthorized` («Ключ не принят»), `validation_failed` («Файл отклонён: …») и прочие коды;
    
- при скачивании создаёт Blob URL, программно кликает по ссылке, затем освобождает URL.
    

Обратите внимание: история хранится **на клиенте**, а не на сервере. Сервер не ведёт список загруженных файлов — он лишь отдаёт их по id. Это осознанное решение: клиент помнит, что он загрузил, но сервер не раскрывает список файлов.

## Шаг 8. API загрузки (`POST /api/files`)

Контроллер защищён атрибутом `[Authorize]` со схемой `ApiKey`, а конкретный метод — политикой `WriteFiles`. Дополнительно на методе стоят лимиты:

- `[RequestSizeLimit]` — ограничение на размер тела запроса;
    
- `[RequestFormLimits(MultipartBodyLengthLimit = …)]` — ограничение на размер multipart‑формы.
    

Оба лимита дублируют глобальный лимит Kestrel — это «defense in depth»: даже если один уровень обойдут, сработает другой.

Логика загрузки:

1. Если файл не передан или пуст — `400` с `ApiError("no_file", …)`.
    
2. Открывается поток файла.
    
3. Вызывается валидатор — проверка размера, расширения, сигнатуры.
    
4. Если невалидно — `400` с `ApiError("validation_failed", …)` и логом предупреждения.
    
5. Если валидно — файл сохраняется, возвращается `201 Created` с `Location` на скачивание и метаданными (id, имя, размер, тип).

## Шаг 9. Валидация файлов (`FileValidationService`)

Принцип — «defense in depth»: проверяются три независимых признака, и файл считается валидным, только если расширение **и** сигнатура входят в whitelist.

Порядок проверок — от дешёвой к дорогой:

1. **Размер**: пустой или больше 10 МБ — отказ. Самая дешёвая проверка, поэтому первая.
    
2. **Расширение**: берётся из имени файла, проверяется по whitelist (`.png`, `.jpg`, `.jpeg`, `.gif`, `.pdf`, `.txt`). Регистронезависимо.
    
3. **Сигнатура**: читаются первые 8 байт потока, поток возвращается в начало. Для `.txt` — проверка, что нет управляющих/бинарных байтов. Для остальных — сравнение с известной сигнатурой:
    
    - PNG: `89 50 4E 47`;
        
    - JPEG: `FF D8 FF`;
        
    - GIF: `47 49 46 38`;
        
    - PDF: `25 50 44 46`.
        

Если сигнатура не совпадает с расширением — отказ. Это защита от подмены: злоумышленник может переименовать `.exe` в `.jpg`, но сигнатура его выдаст.

**MIME‑тип от клиента не используется для решения о валидности** — он тоже подделывается. Он лишь сохраняется в метаданных и отдаётся при скачивании.

## Шаг 10. Хранилище (`LocalFileStorageService`)

**Сохранение**:

- генерируется случайный id — 16 байт криптостойкого генератора, в hex (32 символа). Это **не** оригинальное имя файла: так исключается path traversal и коллизии;
    
- бинарник пишется в `<root>/<id>.bin`;
    
- метаданные (оригинальное имя, размер, content type) пишутся рядом в `<root>/<id>.meta.json`;
    
- корень берётся из конфигурации `Storage:RootPath` или `<base>/uploads`; каталог создаётся при старте.
    

**Открытие**:

- сначала проверяется, что id — 32 hex‑символа. Это защита от path traversal: в id не может быть `../`;
    
- проверяется существование обоих файлов (бинарь и метаданные);
    
- читаются метаданные, парсятся; при ошибке JSON — лог и `null`;
    
- возвращается поток на чтение и метаданные.
    

Важно: файлы лежат **вне webroot**, поэтому `UseStaticFiles` их не отдаёт. Доступ — только через API с проверкой ключа.

## Шаг 11. API скачивания (`GET /api/files/{id}`)

Метод защищён политикой `ReadFiles`. Логика:

1. Открыть файл по id. Если не найден — `404` с `ApiError("not_found", …)`.
    
2. Установить `Content-Disposition: attachment` с именем файла в кодировке UTF‑8 (RFC 5987) — чтобы браузер **скачивал**, а не открывал файл. Это защита от XSS через загруженный HTML/JS.
    
3. Вернуть файл с включённой поддержкой Range‑запросов (докачка, воспроизведение).
    

Даже если злоумышленник загрузит HTML под видом `.txt` (что маловероятно из‑за проверки сигнатуры), браузер его не выполнит: `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` не оставляют шансов.

## Шаг 12. Модель угроз (STRIDE)

Отдельная страница `/Threats` показывает «живой» артефакт безопасности — прямо в приложении, из одного репозитория с кодом.

**Границы доверия** (`TB-01`, `TB-02`, `TB-03`) — линии, где данные переходят из одной зоны доверия в другую. На каждой указано, что пересекает границу и какие контрмеры применяются.

**Угрозы** по STRIDE:

- Spoofing — подмена типа файла;
    
- Tampering — path traversal через имя файла;
    
- Repudiation — отсутствие трассировки;
    
- Information Disclosure — XSS через скачанный файл;
    
- Denial of Service — огромный файл;
    
- Elevation of Privilege — загрузка без аутентификации.
    

У каждой — описание, граница доверия, оценка риска (0–10), контрмеры и ссылки на backlog.

**Security backlog** — конкретные задачи по закрытию угроз: приоритет, статус (`Open`/`InProgress`/`Done`/`Accepted`), краткое описание контрмеры и владелец (backend/qa/devops/frontend).

Каждая угроза должна быть либо устранена кодом/конфигом, либо явно принята с обоснованием — это принцип «threat‑driven development».

## Шаг 13. Обработка ошибок и краевые случаи

- **Ошибки API** возвращаются в едином формате `ApiError(code, message, correlationId)` — без внутренних исключений и стектрейсов. Детали — в логах по correlation id.
    
- **Ошибки клиента** (400/401/403/404/413/415) не повторяются — это ошибки запроса.
    
- **Ошибки сервера** (5xx) и сетевые сбои — повторяемы (в клиенте пока не реализован backoff, но коды различаются).
    
- **Отсутствие файла или метаданных** — `404`, без падений.
    
- **Битый JSON метаданных** — лог и `404`.
    
- **Превышение лимитов** — `413` на уровне Kestrel или `400` на уровне валидатора в зависимости от того, где сработал лимит.
    
- **Abort** (пользователь ушёл со страницы) — корректно пробрасывается как `AbortError`, не логируется как ошибка.

В данном проекте реализован каталог товаров по гибридной схеме: серверный Razor отдаёт HTML‑каркас страницы (заголовок, кнопки‑фильтры по категориям, шаблон карточки), а сами товары подгружаются на клиенте через JSON API. Данные хранятся в JSON‑файле на диске и читаются при каждом запросе.

---

## Шаг 1. Запуск и регистрация сервисов

При старте подключается MVC (контроллеры + представления) и регистрируется репозиторий товаров как **singleton**. Репозиторий читает `Data/products.json`; каждый вызов заново открывает файл, десериализует его целиком в список и фильтрует в памяти. Singleton здесь означает лишь один экземпляр на всё приложение — состояние между вызовами не кешируется.

Дальше настраивается конвейер:

- обработчик исключений и HSTS — только вне Development;
    
- HTTPS‑редирект;
    
- маршрутизация;
    
- авторизация (без настроенной аутентификации — фактически пустой вызов);
    
- `MapStaticAssets()` — отдача статических ресурсов с учётом «отпечатков» (fingerprinting) для агрессивного кеширования;
    
- `MapControllers()` — маршруты атрибутных контроллеров (API);
    
- маршрут по умолчанию `{controller=Home}/{action=Index}/{id?}` с привязкой к статическим ресурсам.
    

Отдельно стоит отметить `MapControllers()`: он нужен, потому что `ProductsController` использует атрибутный маршрут `[Route("api/products")]`, а не стандартный шаблон MVC. Без этого вызова API‑эндпоинты были бы недоступны.

## Шаг 2. Открытие главной страницы (GET `/`)

Маршрут по умолчанию приводит к действию `Index` домашнего контроллера. Контроллер:

1. Получает **все** товары из репозитория.
    
2. Вытаскивает из них уникальные категории, сортирует по алфавиту.
    
3. Формирует модель представления: заголовок «Каталог товаров», адрес API (строится через `Url.Action("List", "Products")` → `/Products/List` или `/api/products` в зависимости от маршрутизации), список категорий.
    
4. Возвращает представление.
    

Ключевой момент: **сами товары в HTML не встраиваются**. В модель попадают только заголовок, адрес API и список категорий. Список товаров строится на клиенте.

Представление `Index.cshtml` рендерит:

- заголовок;
    
- кнопки‑фильтры: «Все» (пустая `data-category`) и по одной кнопке на каждую категорию из модели;
    
- контейнер `#catalog` с `data-endpoint` (адрес API) и `data-loading-text` («Загрузка каталога…»);
    
- шаблон карточки `<template id="product-card-template">` с местами под название, категорию, цену и кнопку «Подробнее»;
    
- скрытый блок ошибок `#catalog-error`.
    

В конце подключается `catalog.js`.

## Шаг 3. Загрузка каталога на клиенте

Скрипт `catalog.js` обёрнут в IIFE со строгим режимом. Сначала он находит контейнер `#catalog`; если его нет — сразу выходит (скрипт безопасно подключать на любой странице).

Далее:

1. Читает из `data-*` адрес API и текст загрузки, находит шаблон и блок ошибок.
    
2. Определяет вспомогательные функции: показать/скрыть ошибку, отформатировать цену через `Intl.NumberFormat('ru-RU')` (разделители тысяч).
    
3. Определяет функцию рендера: если товаров нет — пишет «Ничего не найдено»; иначе клонирует шаблон для каждого товара, заполняет поля по `data-field`, кладёт в кнопку «Подробнее» идентификатор товара, собирает всё в `DocumentFragment` и одной операцией заменяет содержимое контейнера.
    
4. Определяет функцию загрузки: очищает ошибку, ставит текст «Загрузка каталога…», формирует URL (с параметром `category`, если фильтр задан), делает `fetch` с `Accept: application/json`, проверяет `res.ok`, парсит JSON и рендерит. При ошибке показывает сообщение в блоке ошибок.
    
5. Навешивает обработчики на кнопки‑фильтры: клик → загрузка с соответствующей категорией (или без неё для «Все»).
    
6. Навешивает **делегированный** обработчик клика на контейнер каталога — так он работает и для карточек, которые появятся позже.
    
7. Сразу вызывает загрузку без фильтра — каталог отображается при открытии страницы.

## Шаг 4. Запрос списка к API

Клиент обращается к `/api/products` (или `/api/products?category=Мебель` и т. п.). Контроллер API:

- если параметр `category` пустой или состоит из пробелов — берёт **все** товары;
    
- иначе — только с указанной категорией.
    

Сравнение категории **регистронезависимое**, поэтому `мебель`, `Мебель`, `МЕБЕЛЬ` сработают одинаково.

Дальше контроллер **преобразует доменные модели в DTO** (`ProductDto`) — это ключевое отличие API от UI‑экшена. DTO содержит только те поля, которые нужны клиенту: `Id`, `Name`, `Price`, `Category`. Это защита от случайной утечки внутренних полей при росте модели и стабильный контракт для клиента.

Ответ отдаётся через `Json(dtos)` со статусом 200.

Отдельный метод получения товара по числовому id: если товара нет — `404` с телом `{ error: "Product not found", id }`, иначе `200` с DTO.

## Шаг 5. Клик по кнопке «Подробнее»

Обработчик на контейнере ловит клик, проверяет, что цель — кнопка с классом `details-btn` (через `closest`, чтобы работало и при клике по вложенным элементам). Берёт id товара из `data-id`.

Затем делает запрос к `/api/products/{id}`, получает DTO и показывает `alert` с названием, категорией и ценой. При ошибке пишет сообщение в блок ошибок.

---

## Шаг 6. Обработка ошибок и краевые случаи

- **На клиенте**: любая сетевая или HTTP‑ошибка ловится в `try/catch`, логируется в консоль и показывается пользователю в `#catalog-error` (блок становится видимым). Перед каждой загрузкой ошибка скрывается.
    
- **На сервере**: если товар не найден — возвращается `404`, и клиент превращает это в сообщение «Не удалось загрузить товар… HTTP 404».
    
- **Отсутствие файла данных**: репозиторий не падает — возвращает пустой список. Тогда на странице будет «Ничего не найдено», а категорий — пусто.
    
- **Приложение вне режима разработки**: при необработанном исключении срабатывает обработчик `/Home/Error` и показывается страница ошибки с идентификатором запроса; в режиме разработки вместо неё — подробности исключения.

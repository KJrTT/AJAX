В данном проекте реализован REST API книжного магазина с **версионированием**: одновременно живут две версии — v1 и v2. v1 помечена как устаревшая (deprecated), но продолжает работать до указанной даты. Клиенты получают специальные заголовки‑предупреждения, а в Swagger обе версии показаны отдельно. Дополнительно используется feature flag для постепенного включения нового поля без ломающих изменений.

---

## Шаг 1. Запуск и регистрация сервисов

При старте:

- подключаются контроллеры;
    
- репозиторий книг регистрируется как singleton (данные в памяти);
    
- подключается feature management — механизм флагов;
    
- настраивается версионирование API;
    
- настраивается Swagger с отдельной группой на каждую версию.
    

**Версионирование**:

- версия по умолчанию — 1.0;
    
- `AssumeDefaultVersionWhenUnspecified = true` — клиенты без версии получают v1 (обратная совместимость);
    
- `ReportApiVersions = true` — в ответы добавляются заголовки `api-supported-versions` и `api-deprecated-versions`;
    
- версию можно передать **тремя способами**: в пути (`/api/v1/books`), в заголовке `api-version`, в query‑параметре `api-version`. Readers комбинируются — сработает любой.
    

**Swagger** настраивается через отдельный конфигуратор: для каждой описанной версии создаётся свой документ с заголовком «BookStore API», версией и пометкой «DEPRECATED» для устаревших.

Пайплайн:

1. Редирект с `/` на `/swagger`.
    
2. Swagger и Swagger UI — только в Development. В UI показываются обе версии, у deprecated стоит пометка.
    
3. HTTPS‑редирект.
    
4. `DeprecationMiddleware` — добавляет заголовки устаревания к ответам v1.
    
5. Маршрутизация контроллеров.

## Шаг 2. Модели

**Доменная модель `Book`** — то, что хранится: `Id`, `Title`, `Author`, `Price` (decimal), `Isbn`.

**`BookV1Response`** — контракт v1: те же поля, `Price` — просто число. `Isbn` был добавлен как non‑breaking изменение (новое необязательное поле не ломает существующих клиентов).

**`BookV2Response`** — контракт v2: **breaking change** — `Price` теперь объект `Money` с полями `Amount` и `Currency`. Клиент, ожидавший число, сломается — поэтому нужна новая версия.

**`Money`** — пара «сумма + валюта». Валюта по умолчанию — RUB.

**`CreateBookRequest`** — входная модель для v1: валидация (обязательные поля, ограничения длины, диапазон цены).

**`CreateBookV2Request`** — входная модель для v2: `Price` — объект `Money`. Объявлена в конце файла контроллера v2.

## Шаг 3. Репозиторий

`InMemoryBookRepository` хранит список книг, предзаполненный тремя записями. Все операции защищены `lock` — это делает список потокобезопасным при конкурентных запросах.

- `GetAll` — возвращает **копию** списка (`ToList`), чтобы вызывающий код не мог изменить внутреннее состояние;
    
- `GetById` — поиск по id;
    
- `Add` — присваивает очередной id и добавляет книгу;
    
- `Delete` — удаляет по id, возвращает `true`/`false`.
    

Данные теряются при перезапуске — это учебное хранилище.

## Шаг 4. Deprecation‑middleware

Задача — сообщить клиентам v1, что API устарел, и указать дату отключения и замену. Используются стандартные заголовки:

- `Deprecation: true` — сигнал, что версия устарела;
    
- `Sunset: Sat, 31 Dec 2026 23:59:59 GMT` — дата, после которой версия перестанет работать (RFC 8594);
    
- `Link: <…/api/v2/books>; rel="successor-version"` — ссылка на замену;
    
- `Warning: 299 - "…"` — текстовое предупреждение.
    

**Как определяется v1‑запрос**:

1. Если в пути есть `/v2/` — точно не v1.
    
2. Если в пути есть `/v1/` — точно v1.
    
3. Если `api-version=2.0` в query или заголовке — не v1; `1.0` — v1.
    
4. Если путь начинается с `/api/books` (без версии) — считается v1 (по умолчанию).
    

Заголовки добавляются через `OnStarting` — колбэк, который выполняется **перед отправкой ответа**, когда статус и заголовки уже сформированы. Это важно: если поставить заголовки сразу, они могут быть перезаписаны контроллером.

Middleware логирует каждый вызов v1 как warning — это помогает понять, кто ещё пользуется устаревшей версией.

## Шаг 5. Контроллер v1

Маршруты:

- `api/v{version:apiVersion}/books` — с явной версией в пути;
    
- `api/books` — fallback для клиентов без версии (обратная совместимость).
    

**`GetAll`** — интересный пример использования feature flag:

- проверяется флаг `UseFullNameField`;
    
- если включён — в ответ добавляется поле `FullName` (дублирует `Author`);
    
- поле `Author` остаётся всегда — старые клиенты не ломаются;
    
- новый клиент может перейти на `FullName`, когда флаг включат.
    

Это паттерн «expand → migrate → contract»: сначала добавляем новое поле параллельно со старым, потом клиенты мигрируют, потом старое удаляют. Feature flag позволяет включать новое поведение постепенно, без релиза.

**`GetById`** — возвращает `BookV1Response` или `404` с сообщением.

**`Create`** — валидирует входную модель, добавляет книгу, возвращает `201 Created` с `Location` на `GetById` (с указанием версии 1.0) и телом `BookV1Response`.

**`Delete`** — `204 No Content` при успехе, `404` если не найдено.

## Шаг 6. Контроллер v2

Маршрут — только с явной версией в пути: `api/v{version:apiVersion}/books` (fallback на `/api/books` нет — v2 не должна быть версией по умолчанию).

**`GetAll`** — возвращает список `BookV2Response`, где `Price` — объект `Money`.

**`GetById`** — `BookV2Response` или `404`.

**`Create`** — принимает `CreateBookV2Request` с `Money`, извлекает `Amount` для хранения, возвращает `201 Created` с `Location` (версия 2.0) и телом `BookV2Response`.

Приватный метод `Map` преобразует доменную `Book` в `BookV2Response`: цена оборачивается в `Money` с валютой RUB.

---

## Шаг 7. Как работает маршрутизация версий

Один и тот же путь `/api/v1/books` (или `/api/v2/books`) обрабатывается **разными контроллерами** из пространств имён `Controllers.V1` и `Controllers.V2`. Это возможно благодаря атрибуту `[ApiVersion("1.0")]`/`[ApiVersion("2.0")]` и маршруту с плейсхолдером `{version:apiVersion}`.

Когда приходит запрос:

1. Версия извлекается из пути, заголовка или query (в порядке, заданном readers).
    
2. Если версия не указана — подставляется 1.0 (из‑за `AssumeDefaultVersionWhenUnspecified`).
    
3. Маршрутизация выбирает контроллер с соответствующей версией.
    
4. В ответ добавляются `api-supported-versions` и `api-deprecated-versions` (из‑за `ReportApiVersions`).
    

Клиент может комбинировать: `/api/v1/books`, `/api/books?api-version=2.0`, `/api/books` с заголовком `api-version: 2.0` — во всех случаях сработает нужная версия.

## Шаг 8. Swagger

В Development доступны:

- `/swagger` — UI с двумя группами: «V1 (deprecated)» и «V2»;
    
- `/swagger/v1/swagger.json` и `/swagger/v2/swagger.json` — отдельные описания.
    

Конфигуратор Swagger проходит по всем описанным версиям и для каждой создаёт документ. У deprecated в описании — предупреждение и дата sunset. Это позволяет клиентам видеть, какая версия актуальна, прямо из документации.

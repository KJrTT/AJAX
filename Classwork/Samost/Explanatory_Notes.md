В данном проекте реализован минимальный REST API для работы с товарами: создание, получение по идентификатору и получение всего списка. Данные хранятся в памяти процесса. Дополнительно подключён Swagger для документации API. В конце файла контроллера лежит отдельный минимальный пример с одним эндпоинтом, не связанный с основной логикой.

---

## Шаг 1. Запуск и регистрация сервисов

При старте:

- подключаются контроллеры (`AddControllers`) — без представлений, потому что это чистое API;
    
- включается исследователь API‑эндпоинтов (`AddEndpointsApiExplorer`) — нужно, чтобы Swagger мог собрать метаданные о маршрутах;
    
- включается генератор Swagger (`AddSwaggerGen`) — документирует API;
    
- `ProductService` регистрируется как **singleton**.
    

Singleton здесь важен, потому что сервис хранит состояние — статический список товаров и счётчик идентификаторов. Если бы сервис был transient или scoped, каждый запрос получал бы новый экземпляр, но благодаря тому, что список и счётчик объявлены **статическими**, состояние всё равно было бы общим. Фактически состояние живёт на уровне типа, а не экземпляра.

Дальше настраивается конвейер:

- в режиме разработки включаются Swagger и Swagger UI;
    
- HTTPS‑редирект;
    
- маршрутизация контроллеров (`MapControllers`).
    

Обратите внимание: нет `UseRouting`/`UseEndpoints` в явном виде — `MapControllers` в минимальной модели сам подключает нужные этапы. Нет и аутентификации/авторизации — API открыт.

## Шаг 2. Модель и DTO

**Доменная модель `Product`** — то, что хранится и возвращается клиенту: `Id`, `Name`, `Price`, `CategoryId`.

**DTO `CreateProductDto`** — то, что клиент присылает при создании. Отдельный тип нужен, чтобы:

- не позволять клиенту задавать `Id` (он присваивается на сервере);
    
- отделить контракт API от внутренней модели (при росте модели внутренние поля не утекут наружу);
    
- навесить валидационные атрибуты именно на входные данные.
    

Атрибуты валидации:

- `Name` — обязательное, длина от 3 до 50 символов;
    
- `Price` — больше 0 (диапазон от 0.01 до максимума `decimal`);
    
- `CategoryId` — больше 0.
    

Сообщения об ошибках на русском — они попадут в ответ при невалидном запросе.

## Шаг 3. Сервис

`ProductService` — тонкая обёртка над статическим списком:

- `GetAll` — возвращает список как `IReadOnlyList`, чтобы вызывающий код не мог его изменить;
    
- `GetById` — ищет по идентификатору, возвращает `null`, если не нашёл;
    
- `Add` — присваивает очередной идентификатор (счётчик увеличивается после присваивания), создаёт `Product` из DTO, добавляет в список и возвращает созданный объект.
    

Важные детали:

- список и счётчик **статические**, поэтому общие для всех экземпляров сервиса;
    
- список **не потокобезопасный**: при одновременных POST‑запросах возможны гонки — два запроса могут получить одинаковый `Id`, или `Add` может выполниться некорректно при одновременной модификации;
    
- данные теряются при перезапуске приложения.

## Шаг 4. Создание товара (POST `/api/products`)

Клиент присылает JSON с полями `name`, `price`, `categoryId`. Контроллер:

1. Получает DTO из тела запроса.
    
2. Проверяет `ModelState`. Благодаря атрибуту `[ApiController]` валидация выполняется автоматически **до** входа в метод. Но контроллер всё равно проверяет `ModelState` явно и возвращает `ValidationProblem` — это даёт стандартизированный ответ с описанием ошибок по полям (формат Problem Details).
    
3. Если валидация прошла — вызывает `Add` у сервиса.
    
4. Возвращает `201 Created` с заголовком `Location`, указывающим на `GetById` с id созданного товара, и телом — созданным товаром.
    

`CreatedAtAction` — правильный способ ответить на создание ресурса: клиент сразу знает, где этот ресурс можно получить.

---

## Шаг 5. Получение товара по id (GET `/api/products/{id}`)

Маршрут ограничен числовым id (`{id:int}`), поэтому строка вместо числа не попадёт в этот метод — вернётся 404 от маршрутизации.

Контроллер:

- ищет товар в сервисе;
    
- если не нашёл — `404 Not Found` без тела;
    
- если нашёл — `200 OK` с товаром.
    

---

## Шаг 6. Получение всех товаров (GET `/api/products`)

Контроллер возвращает `200 OK` со списком всех товаров. Если список пуст — вернётся пустой массив, а не ошибка.

---

## Шаг 7. Swagger

В режиме разработки доступны:

- `/swagger/v1/swagger.json` — описание API в формате OpenAPI;
    
- `/swagger` — интерактивная страница Swagger UI, где можно посмотреть эндпоинты и отправить тестовые запросы.
    

Swagger собирает метаданные из атрибутов контроллера (`[ApiController]`, `[Route]`, `[HttpPost]`, `[HttpGet]`) и из DTO. Вне режима разработки Swagger не подключается — это стандартная практика, чтобы не раскрывать описание API в продакшене.

## Шаг 8. Отдельный минимальный пример

В конце файла контроллера лежит независимый фрагмент:

- создаётся билдер и приложение;
    
- регистрируется один эндпоинт `GET /hello`, возвращающий строку «Hello, World!»;
    
- приложение запускается.
    

Это пример Minimal API: без контроллеров, без DTO, без сервисов — эндпоинт задаётся прямо в коде. Фрагмент не связан с основной логикой и, судя по всему, демонстрирует альтернативный стиль определения маршрутов. В реальном проекте так не делают — это отдельный пример, а не часть работающего приложения.
